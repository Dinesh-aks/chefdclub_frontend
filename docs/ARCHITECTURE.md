# ChefdClub Frontend — Architecture

This document defines the architecture, design system, and conventions for
`chefdclub_frontend`. It is the reference for how code is organized and how future
pages/features should be built. Update it whenever a structural or design-token decision
changes.

## 1. Frontend architecture

- **Framework:** Next.js (App Router), React, TypeScript (strict mode).
- **Styling:** Tailwind CSS v4 + shadcn/ui (Radix-based) + Framer Motion for animation.
- **Pattern:** Feature-based architecture inside a `src/` directory.
- **Backend:** A separate service — `chefdclub_backend` (Node.js + Express + TypeScript +
  Prisma + MySQL). This repository contains **no** database code, ORM code, or credentials.
  All data access happens over REST from the browser/server components to that backend.
- **Rendering default:** Server Components. Client Components are the exception, opted into
  explicitly (see §4).
- **Visual reference:** the uploaded Chef'd Club designs (dark "ink" hero/footer sections
  alternating with warm "paper" content sections, serif display headlines with an italic red
  accent, small uppercase tracked labels/nav/buttons). New UI should match this identity —
  see §15 (Design tokens) and §16 (Typography).

## 2. Folder responsibilities

```
src/
├── app/
│   ├── (website)/     # Public website route group — has its own layout (Header + Footer)
│   ├── admin/         # Admin route group (implemented later; auth via backend)
│   ├── layout.tsx     # Root layout — fonts + global providers only, no chrome
│   └── globals.css    # Tailwind entry + design tokens (see §15)
│
├── components/
│   ├── ui/            # shadcn/ui primitives only (generated via `npx shadcn add`)
│   ├── shared/        # Reusable design-system components used across website AND admin
│   ├── website/       # Website chrome + components (Header, Footer, Navigation, ...)
│   └── admin/         # Components specific to the admin panel
│
├── features/          # Feature modules (see §22)
│   ├── website/       # Public marketing site — one folder per page area (home, menus, …)
│   └── admin/         # Admin panel — mirrors app/admin routes
│
├── lib/
│   ├── api/           # Backend API client (fetch wrapper, shared request logic)
│   ├── motion/        # Shared Framer Motion variants (see §19)
│   ├── utils/         # Framework-agnostic utility functions (e.g. `cn`)
│   └── constants/     # Shared constant values (enums, config maps, etc.)
│
├── hooks/              # Shared React hooks (cross-feature only)
├── types/              # Shared TypeScript types/interfaces (cross-feature only)
└── config/             # Static site config: `site.ts` (brand/contact info), `nav.ts`
                         # (nav links). No business/feature logic.
```

Rules for these folders:

- `components/ui` is **only** for shadcn/ui primitives (as generated, then themed via
  `globals.css` tokens — see §15). Do not put business logic there.
- `components/shared` is for generic, feature-agnostic design-system UI (`Container`,
  `Section`, `Heading`, `TextLink`, `Logo`, `Reveal`, `StaggerGroup`) reused across the
  website and admin.
- `components/website` holds chrome/UI tied to the public site but not specific to one
  feature (`Header`, `Footer`, `Navigation`, `MobileNav`). `components/admin` is the
  equivalent for the admin panel once it exists.
- `features/website/` holds one folder per public page area (e.g. `features/website/menus`,
  `features/website/journal`), created only when that feature is implemented — not up front.
- `features/admin/` holds admin screens, grouped by route (e.g. `features/admin/cms/faqs`).
- `hooks/`, `types/`, and `lib/` at the root are for code shared by **multiple** features. A
  hook or type used by only one feature belongs inside that feature's own folder instead.

## 3. Component conventions

- One component per file. File name matches the component: `Header.tsx` exports `Header`.
- `components/ui` files follow shadcn/ui's own naming (kebab-case filenames, e.g.
  `dropdown-menu.tsx`), left as generated by the CLI.
- Everything outside `components/ui` uses PascalCase filenames for components.
- Co-locate a component's own styles/variants/sub-parts in the same file unless it grows
  large enough to warrant a folder (`ComponentName/index.tsx` + siblings).
- Do not duplicate a component that already exists in `components/ui` or `components/shared`
  — extend or compose it instead. (This is why the brand's uppercase/tracked button style was
  added directly to `components/ui/button.tsx` rather than wrapped in a second Button.)

## 4. Server vs. Client Component rules

- **Default to Server Components.** Do not add `"use client"` unless the component actually
  needs one of:
  - React state/effects (`useState`, `useEffect`, etc.)
  - Event handlers (`onClick`, `onChange`, ...)
  - Browser-only APIs (`window`, `localStorage`, ...)
  - A third-party library that itself requires the client runtime (e.g. Framer Motion)
- Push `"use client"` as far down the tree as possible — wrap only the interactive leaf, not
  the whole page or layout. Example: `Header` is a Server Component; only `MobileNav`'s
  underlying `Sheet` primitive is a Client Component, so `"use client"` never appears in
  `Header.tsx` itself.
- `page.tsx` files stay focused on composition and routing: fetch/compose data and render
  components. Business/feature logic (data shaping, validation, API calls) lives in
  `features/<feature>/` or `lib/`, not inline in `page.tsx`.
- Providers that must wrap the whole app (e.g. `TooltipProvider`) are mounted once in
  `app/layout.tsx`. Providers/chrome specific to the website (`Header`/`Footer`) are mounted
  in `app/(website)/layout.tsx` instead, so the admin route group isn't forced to carry them.

## 5. API communication approach

- The frontend **never** talks to MySQL or Prisma directly. All data comes from
  `chefdclub_backend` over REST.
- The base URL is read from the `NEXT_PUBLIC_API_URL` environment variable — never hardcoded.
- `src/lib/api/core/client.ts` provides the single shared `apiFetch<T>(path, options)` helper and
  an `ApiError` class. This is intentionally minimal: it does not know about any specific
  feature or endpoint.
- Feature-specific API calls (e.g. `getMenuItems()`, `createReservation()`) are added inside
  that feature's own folder (`features/<feature>/api.ts`) and built on top of `apiFetch`,
  once that feature is actually implemented — not added speculatively.
- Prefer calling the API from Server Components / Server Actions where possible; use it from
  Client Components only when the interaction genuinely requires client-side fetching
  (e.g. a form submission, live search).

## 6. TypeScript conventions

- `strict: true` is enabled (`tsconfig.json`), plus `noUncheckedIndexedAccess`,
  `noImplicitReturns`, `noFallthroughCasesInSwitch`. Do not weaken these.
- `any` is not allowed. Use `unknown` plus narrowing, or a proper generic/type.
- Shared types live in `src/types/`; feature-only types live inside that feature's folder.
- Prefer `interface` for object shapes that represent entities/props, `type` for unions,
  utility types, and function signatures.
- Name types/interfaces for what they represent, not how they're used
  (`MenuItem`, not `MenuItemPropsType`).

## 7. Environment variables

- `NEXT_PUBLIC_API_URL` — base URL of the `chefdclub_backend` REST API
  (e.g. `http://localhost:5000/api`). Required for any API call.
- `.env.example` documents every variable the app needs, with safe placeholder values (committed).
- `.env` holds real local values — copy from `.env.example`, gitignored, never commit secrets.
- Do not add `.env.local` or mode-specific env files unless the team explicitly needs them; keep one local file (`.env`) aligned with the backend.
- Only variables actually read by the app belong here. Server-only secrets (if any are ever
  needed for this app, e.g. a server-side-only token) must **not** use the `NEXT_PUBLIC_`
  prefix, since that prefix exposes the value to the browser bundle.
- No database credentials of any kind belong in this repository, ever.

## 8. Accessibility rules

- Use semantic HTML elements first; reach for ARIA only when semantics can't express the
  pattern.
- All interactive elements must be reachable and operable via keyboard (shadcn/ui primitives,
  built on Radix, provide this by default — don't undermine it by replacing native elements
  with non-interactive `div`s).
- Every custom interactive element (`TextLink`, nav links, footer links, the `Logo`) carries
  visible `focus-visible` ring styles — don't remove them without replacing them.
- Images require meaningful `alt` text (empty `alt=""` only for purely decorative images).
- Respect color contrast — the tone-system colors (§15) were chosen to hold WCAG AA contrast
  for body text; verify any new color pairing before using it for text.
- Forms: every input has an associated `<Label>`, and errors are announced
  (e.g. `aria-describedby`, `aria-invalid`) — shadcn's `form.tsx` (React Hook Form + Zod)
  already wires this up.
- Motion respects `prefers-reduced-motion` — see §19 (`Reveal`/`StaggerGroup` already do this
  automatically via `useReducedMotion`).

## 9. Responsive design rules

- Design mobile-first; add `sm:`/`md:`/`lg:`/`xl:` overrides as the layout needs to change,
  not the other way around. Tailwind's default breakpoints are used as-is (see §18) — mapped
  to mobile / tablet / desktop / large desktop.
- Avoid fixed pixel widths for layout containers; use `Container` (§17) and relative units.
- Verify every new page/component at common breakpoints (mobile, tablet, desktop, large
  desktop) before considering it done.

## 10. Admin architecture

- The admin panel lives in the **same** Next.js app, under the `/admin` route
  (`src/app/admin/`), and is **not implemented yet** — only the folder location is reserved.
- Admin-specific components go in `components/admin/`; admin-specific features go in
  `features/<feature>/` and are surfaced under `app/admin/...` routes.
- Authentication and authorization are handled by `chefdclub_backend`, not by this frontend.
  The frontend will attach whatever the backend requires (e.g. a bearer token/session cookie)
  to requests made via `lib/api`, but does not implement auth logic itself
  (no password handling, no session storage design, no DB-backed user lookups here).
- Until auth is implemented, do not add any admin routes, links, or UI that imply admin
  functionality exists.
- The admin panel is a utility tool, not part of the marketing brand — if it ever needs a
  user-toggleable light/dark mode, that's a legitimate, separate use of the `.dark` class /
  `@custom-variant dark` already declared (but unused) in `globals.css`. It is **not** the
  same mechanism as the website's fixed `.tone-ink` brand tones (§15) — do not conflate them.

# Design system

The public website is built entirely from the primitives below — `Container`, `Section`,
`Heading`, `TextLink`, the shadcn/ui `Button`, `Logo`, `Reveal`/`StaggerGroup` — plus
`Header`/`Footer`/`Navigation`/`MobileNav` for site chrome. No page exists yet; when one is
built, compose it from these rather than writing new one-off layout/typography/color code.

## 11. Design principle: centralized tokens, no scattered values

Colors, radius, and letter-spacing live as CSS custom properties / Tailwind theme keys in
`src/app/globals.css`, consumed through Tailwind utilities (`bg-primary`, `text-foreground`,
`rounded-md`, `tracking-mega`, ...). Spacing/width rhythm lives in the `Container` and
`Section` components. **Never hardcode a hex color, one-off spacing value, or arbitrary
letter-spacing in a page or feature component** — add or reuse a token/component instead.

## 12. Colors & tone system

Chef'd Club's identity alternates two **fixed brand surfaces** — a dark "ink" section and a
warm "paper" section — as a design choice, not a user/OS light-dark preference. Because of
this, the public site does **not** implement `prefers-color-scheme`/next-themes dark mode.

Instead, `globals.css` defines the standard shadcn/ui semantic color slots
(`background`, `foreground`, `card`, `popover`, `primary`, `secondary`, `muted`, `accent`,
`destructive`, `border`, `input`, `ring`) once for the default "paper" surface, and a
`.tone-ink` class that **re-scopes the same variable names** for the dark surface:

```css
:root { --background: #ede7dc; --foreground: #211e1b; --primary: #a3232b; /* ... */ }
.tone-ink { --background: #1b1918; --foreground: #f3efe7; /* card/muted/accent/border... */ }
```

`primary`/`ring`/`destructive` intentionally stay identical on both tones — the brand red CTA
looks the same on a light or dark section.

Because every shadcn/ui component (`Button`, `Card`, `Input`, `Badge`, `Sheet`, `Tooltip`,
`Select`, ...) is already built from these same variable names, **any component dropped
inside a `.tone-ink` scope automatically renders correctly** with no special-casing. Use it
via the `Section` component's `tone` prop:

```tsx
<Section tone="ink">...</Section>   {/* dark hero/footer-style section */}
<Section tone="default">...</Section> {/* warm paper section (default) */}
```

Do not build a new color prop/variant system per component — if a component needs to look
right on both tones, it should just reference the semantic Tailwind classes
(`bg-background`, `text-foreground`, `text-muted-foreground`, `border-border`, ...), not the
literal hex values.

## 13. Typography & fonts

Two font families, loaded via `next/font/google` in `app/layout.tsx` and exposed as CSS
variables consumed by Tailwind's `font-sans`/`font-serif` utilities:

| Role | Font | Tailwind utility | Usage |
|---|---|---|---|
| Display / headings | "Bodoni Moda", Didot, "Bodoni 72" (incl. italic) | `font-serif` | `Heading`, standalone quotes/pull-quotes |
| Body / UI | Jost (weights 300/400/500, incl. italic) | `font-sans` (site default) | paragraphs, nav, buttons, labels |

- The italic, sometimes red-colored accent phrase seen inside headlines
  (*"...with a hint of opulence."*) is authored by the page, not baked into `Heading`: wrap
  the phrase in `<em>` (italic) or `<em className="text-primary">` (italic + brand red).
- Small uppercase tracked labels (nav items, eyebrows, buttons, footer column titles) use the
  `tracking-mega` utility (`letter-spacing: 0.2em`, defined once in `globals.css` — see §11)
  together with `text-xs uppercase`. Don't reach for an arbitrary `tracking-[...]` value.
- Heading sizes are controlled by `Heading`'s `size` prop (`display` | `section` |
  `subsection`) — see §14 — not by writing `text-*` classes ad hoc on a page.

## 14. Shared components

| Component | Path | Purpose |
|---|---|---|
| `Container` | `components/shared/Container.tsx` | Centralized max-width (`max-w-7xl`) + responsive gutter. Every section's content sits inside one. |
| `Section` | `components/shared/Section.tsx` | Vertical rhythm (`py-16 md:py-24 lg:py-32`) + tone (`default` \| `ink`, §12). The building block every page section is made from. |
| `Heading` | `components/shared/Heading.tsx` | Eyebrow label (small rule + tracked text) + serif headline, with `size`/`align`/`as` props. |
| `TextLink` | `components/shared/TextLink.tsx` | The small uppercase tracked inline link pattern ("Explore the menus", "Read the essay"), with an `arrow` variant for CTAs like "Reserve a date →". |
| `Logo` | `components/shared/Logo.tsx` | The "Chef **'d** Club" wordmark (red italic apostrophe) + "Singapore" sub-label. Used in `Header` and `Footer`. |
| `Reveal` / `StaggerGroup` | `components/shared/Reveal.tsx`, `StaggerGroup.tsx` | Framer Motion scroll-reveal wrappers — see §19. |
| `Button` | `components/ui/button.tsx` | shadcn primitive, themed for the brand (uppercase, `tracking-mega`, sharp corners via the radius token) directly in its `cva` — no separate wrapper (see §3). |

**Justification for what's *not* here yet:** no page-specific components (menu cards,
gallery grids, reservation forms, etc.) exist — they're built inside `features/<feature>/`
only once that feature is implemented (§22). No `Terms`/legal page component either, for the
same reason.

## 15. Design tokens reference

| Token role | Variable | Default ("paper") | `.tone-ink` |
|---|---|---|---|
| Radius | `--radius` | `0.25rem` (sharp, near-square corners — matches the brand's crisp buttons/cards) | same |
| Background / Foreground | `--background` / `--foreground` | `#ede7dc` / `#211e1b` | `#1b1918` / `#f3efe7` |
| Card / Popover | `--card` / `--popover` | `#f8f5ef` | `#232020` |
| Primary (brand red CTA) | `--primary` / `--primary-foreground` | `#a3232b` / `#fbf8f3` | same |
| Muted (secondary text) | `--muted-foreground` | `#6b655c` | `#a79f92` |
| Border | `--border` | `#dcd3c0` | translucent white (`color-mix`) |
| Letter-spacing | `--tracking-mega` | `0.2em` | — |

Shadows are intentionally minimal: the reference design is flat, using hairline `border`s to
separate content instead of drop shadows. Reserve `shadow-sm`/`shadow-md` for floating UI
that already ships with it by default (popovers, dropdowns, dialogs, sheets) — don't add
shadows to page sections/cards for decoration.

## 16. Buttons & links

- **Solid CTA** → `Button` (`components/ui/button.tsx`), `variant="default"`. Renders
  uppercase, tracked, brand-red, sharp-cornered — matches "RESERVE A DATE" in the reference.
  Use `variant="outline"`/`"secondary"`/`"ghost"` for lower-emphasis actions; all inherit the
  same uppercase/tracked treatment since it's set on the shared base style.
- **Inline text link** → `TextLink` (§14), for links embedded in body copy or paired next to
  a `Button` (e.g. "Reserve a date" button + "Explore the menus" text link side by side, as
  in the hero). Use `variant="arrow"` for a link that acts as its own CTA.
- **Site navigation link** → plain `next/link` styled inline in `Navigation`/`MobileNav`/
  `Footer` (uppercase, tracked, no underline until hover) — these aren't `TextLink` because
  they don't use the underline styling, only the tracked-uppercase type treatment.
- Every link/button variant carries a `focus-visible` ring — never remove it.

## 17. Spacing, containers & section layout

- **Container width:** `max-w-7xl` (1280px), with `px-4 sm:px-6 lg:px-8` gutters — defined
  once in `Container` (§14). Don't hardcode a different max-width per page.
- **Vertical rhythm:** every section uses `Section`'s default `py-16 md:py-24 lg:py-32`. If a
  section genuinely needs different spacing (a tighter CTA banner, say), override via
  `className` on that one `Section` instance rather than inventing a new pattern.
- **Section anatomy**, matching the reference: optional `Heading` (eyebrow + serif title,
  optionally with a supporting paragraph) → content (text columns, card grid, image grid,
  form) → optional `TextLink`/`Button` CTA. Alternate `tone="default"`/`tone="ink"` between
  sections down the page the way the reference does.
- For a full-bleed section (edge-to-edge image/video), pass `container={false}` to `Section`
  and place your own `Container` around just the text content inside it.

## 18. Responsive breakpoints

Tailwind v4's default breakpoint scale is used as-is — no custom breakpoints:

| Breakpoint | Width | Maps to |
|---|---|---|
| *(default)* | 0 | Mobile |
| `sm` | 640px | Large mobile / small tablet |
| `md` | 768px | Tablet |
| `lg` | 1024px | Desktop (also where `Navigation` switches from `MobileNav` to inline links) |
| `xl` | 1280px | Large desktop |

Build mobile-first (unprefixed classes = mobile), then layer `sm:`/`md:`/`lg:`/`xl:` as the
design actually changes at that width — don't add a breakpoint override "just in case."

## 19. Animation conventions (Framer Motion)

Motion should read as premium and quiet, never decorative-for-its-own-sake. Reusable variants
live in `src/lib/motion/variants.ts`; reusable wrapper components live in `components/shared`:

| Variant / component | Use for |
|---|---|
| `fadeIn` | Simple opacity-only reveal (e.g. a background image easing in). |
| `fadeInUp` (default for `Reveal`) | Standard section/element scroll-reveal — the workhorse. |
| `staggerChildren` + `StaggerGroup` | A row/grid of items (gallery tiles, feature cards) that should reveal one after another rather than all at once. |
| `imageReveal` | A slightly-scaled-in image reveal for hero/feature imagery. |

Usage:

```tsx
<Reveal><Heading ...>...</Heading></Reveal>

<StaggerGroup className="grid grid-cols-3 gap-6">
  {items.map((item) => (
    <motion.div key={item.id} variants={fadeInUp}>...</motion.div>
  ))}
</StaggerGroup>
```

Rules:

- Both `Reveal` and `StaggerGroup` call `useReducedMotion()` and skip the animation entirely
  when the user prefers reduced motion — don't bypass this.
- Animate on scroll-into-view (`whileInView`, `once: true`) for page content; reserve
  hover/tap micro-interactions for genuinely interactive elements (buttons, cards you can
  click), and keep them subtle (opacity/translate/scale, not spins or bounces).
- **Page transitions are not implemented yet** — there are no pages to transition between.
  When needed, the convention will be a root `app/(website)/template.tsx` with
  `AnimatePresence`, added once real routes exist — don't scaffold it speculatively now.

## 20. Image conventions

No real imagery exists yet, but every future page will follow these rules:

- Always use `next/image`, never a plain `<img>` — required for responsive sizing and
  optimization.
- Always set an explicit aspect ratio on the wrapping element (`aspect-[4/3]`,
  `aspect-square`, `aspect-video`, etc.) combined with `fill` + `object-cover`, rather than
  fixed pixel `width`/`height`, so images stay responsive at every breakpoint.
- Use `object-position` (`object-top`, `object-[center_30%]`, etc.) instead of cropping the
  source image, when a dish/plate needs different framing per aspect ratio.
- The gallery/spotlight "captioned image" pattern (dish name + category label over a dark
  gradient at the bottom of the photo, seen throughout the reference) is common enough to
  become a shared component **once the Gallery/Home features are actually built** — it was
  intentionally not built speculatively in this phase (no real images to design it against
  yet). When it is, it belongs in `components/shared` (used by Home, Gallery, and Journal).
- Always provide meaningful `alt` text describing the dish/scene — never reuse the caption
  text verbatim if the caption is purely stylistic (e.g. a category badge).

## 21. Navigation, header & footer conventions

- `Header` (`components/website/Header.tsx`) is mounted once, in `app/(website)/layout.tsx`
  — never re-added inside individual pages. It always renders in the `ink` tone regardless of
  the page content beneath it, matching the reference (dark header on every page).
  - A "utility bar" (service tags + hours/phone) shows above the main row on `lg:` and up
    and is hidden on smaller screens to keep the mobile header compact.
  - `Navigation` renders the inline link row from `lg:` up; below that, `MobileNav` renders a
    hamburger button that opens a `Sheet` (also `ink`-toned) with the same links.
  - Nav link data lives in `src/config/nav.ts` (`primaryNav`, `reserveNavItem`, `footerNav`)
    — add a page's route there once it exists, don't hardcode link arrays per component.
- `Footer` (`components/website/Footer.tsx`) is likewise mounted once in the website layout.
  It reads the same `footerNav` config plus `siteConfig` (`src/config/site.ts`) for brand
  description/address/phone/email/hours/social links — update that config, not the component,
  when contact details change.
- Both intentionally live outside `app/layout.tsx` (the true root layout), so the `/admin`
  route group never inherits public-website chrome.

## 22. Rules for adding future features

When a real feature (menu, gallery, films, chef, journal, contact, reservations, etc.) is
ready to be implemented:

1. For the public site, create `src/features/website/<feature-name>/` (kebab-case). For
   admin, add under `src/features/admin/…` following existing route folders.
2. Inside it, keep feature-specific pieces close together, e.g.:
   ```
   features/website/<feature-name>/
   ├── components/   # UI used only by this feature
   ├── api.ts         # calls to lib/api's apiFetch, scoped to this feature
   ├── types.ts       # types used only by this feature
   └── hooks.ts       # hooks used only by this feature (if any)
   ```
   Only create the files/folders a given feature actually needs — don't scaffold empty ones.
3. Add the route under `app/(website)/<route>` or `app/admin/<route>`; the `page.tsx` there
   composes feature components/data using the design-system primitives above (`Section`,
   `Heading`, `Container`, ...) — it does not contain feature logic itself.
4. Promote code to `components/shared`, `hooks/`, `types/`, or `lib/` only once a second
   feature needs the same thing — not preemptively (this is why the "captioned image"
   component from §20 wasn't built yet).
5. Do not introduce a global state library (Redux/Zustand/etc.) unless a feature has a real,
   demonstrated cross-tree state-sharing need that Server Components + URL state + local
   state cannot solve.
6. Every new feature should be checked against §4 (Server/Client split), §8 (accessibility),
   and §9 (responsive) before being considered complete.
